# Коммиты

Коммит читают потом и без контекста сессии: ищут, когда и зачем изменилось поведение (`git log`,
`git blame`), откатывают одно изменение (`git revert`), ищут, где сломалось (`git bisect`). Хороший
коммит делает всё это дешёвым. Обязательное — R-002, R-003, R-004, R-006, R-011: их текст — в сводке
правил при старте сессии или в `standard rules --brief`. Формат, принятый в проекте, — в его
`CONTRIBUTING.md`; он важнее примеров отсюда.

## Всегда

- **Коммить только то, что понимаешь.** Файл в `git status`, про который не знаешь, откуда в нём
  правка, — не твой: возможно, человек работает рядом. Не добавлять, спросить.
- **Индекс собирать по путям**: `git add <путь>…`. `git add -A`, `git add .`, `git commit -a` —
  только когда `git status` показал ровно это изменение и ничего больше.
- **Хук отклонил коммит — коммита нет.** Исправить причину, снова `git add` и `git commit`. Не
  `--amend`: он перепишет предыдущий, уже хороший коммит. Не `--no-verify`: обход прячет нарушение,
  а не исправляет его, и оно остаётся в истории.
- **Отправленное не переписывать.** `--amend`, `reset`, `rebase` — только для коммитов, которые ещё
  никуда не ушли: ни на сервер, ни в пакет переноса. Ошибку в отправленном исправляет новый коммит
  или `git revert`.
- **Автор — человек, который отвечает за коммит.** `user.name`, `user.email` и `--author` не трогать.
- **Когда коммитить — как договорено с человеком**: в инструкциях проекта (`CLAUDE.md`, `AGENTS.md`)
  или в просьбе. Не договорено — показать разбиение и сообщения, коммитить после согласия.
  Отправлять на сервер — только по просьбе.

## Как резать (R-006)

Одно ли это изменение — три вопроса:

1. Сказать, что сделано, одной фразой без «а также» получается?
2. `git revert` этого коммита убирает ровно одну вещь и не ломает соседнее?
3. После коммита проект собирается, а тесты не падают?

«Нет» на первый или второй — коммитов должно быть больше. «Нет» на третий — коммит не закончен:
доделать или склеить с соседним; нерабочее промежуточное состояние ломает `git bisect` и откат.

| Ситуация | Как резать |
|---|---|
| Рефакторинг готовит новое поведение | Два коммита: сначала рефакторинг (в теле — «поведение не меняется»), потом поведение |
| Переименование или перенос файла | Отдельный коммит без правок содержимого: иначе git может не узнать файл, и `git log --follow` оборвётся |
| Переформатирование, автоформатер, концы строк | Отдельный коммит, и в нём больше ничего |
| Исправление ошибки | Вместе с тестом, который её ловит |
| Новая зависимость для новой функции | Вместе с кодом, который её использует; манифест и lock-файл — в одном коммите |
| Обновление версий зависимостей | Отдельный коммит |
| Сгенерированный файл, который проект хранит в git | Вместе с исходником, из которого он получен |
| Попутно замеченная ошибка или опечатка в другом месте | Отдельный коммит или пометка человеку, но не внутри текущего |
| Изменения `.standard/` от команд `standard` | Отдельный коммит, не вместе с кодом задачи |

Слишком мелко — тоже плохо: «поправить опечатку в прошлом коммите», «шаг 2 из 5», «вернуть случайно
удалённое». До отправки такие коммиты склеиваются с тем, к которому относятся.

Резать по ходу дешевле, чем потом: делай изменения по одному и доводи каждое до коммита, прежде чем
браться за следующее. Перед рискованной правкой готовое — в коммит: это точка возврата.

## Документация к изменению (R-011)

- Каждое изменённое имя — опцию, команду, переменную окружения, поле конфига, код ошибки, адрес
  API — найти: `git grep -n "<имя>"`. Найденное в `README.md`, `docs/`, `CONTRIBUTING.md`, примерах
  конфигов, справке `--help`, каталоге ошибок — прочитать и поправить.
- Комментарий и docstring у изменённого кода — тоже документация.
- Решение, которое проживёт дольше пары месяцев, — ADR вместе с кодом, если проект их ведёт.
- Поведение не изменилось (рефакторинг, тесты) — документацию ради галочки не трогать.
- Давняя неточность в документации, не связанная с изменением, — отдельный коммит.
- Документация не опережает код: описание того, чего ещё нет, ждёт коммита с кодом.

## Сообщение (R-004)

Форму первой строки проверяет хук; здесь — о содержании. Сообщение отвечает на два вопроса: что
изменилось и зачем. Как — видно из diff.

**Первая строка** — суть изменения законченной фразой, глагол в неопределённой форме: «Добавить…»,
«Исправить…», «Убрать…», «Перенести…», «Не терять…». Предмет — в словах проекта и его поведения, а
не в именах файлов. Точки в конце нет. Коротко не выходит — скорее всего, это два коммита.

**Тело** — через пустую строку, строки до ~72 знаков. Нужно, когда из diff не видно: какая была
проблема, почему решено так и что отвергли, что знать тому, кто будет обновлять или откатывать
(миграция, несовместимость, порядок выкладки). Пересказывать diff не нужно; мелкому изменению
хватает первой строки.

**Читатель — человек без контекста сессии.** Не писать «как просили», «по итогам обсуждения», «по
замечаниям ревью», номера шагов плана, ссылки на чат и на файлы, скрытые от git (память, планы,
черновики). Ссылаться — на то, что есть у всех: путь в репозитории, хеш коммита, номер задачи на
сервере, если так принято в проекте.

| Плохо | Что не так |
|---|---|
| `Правки`, `WIP`, `fix`, `Обновить код` | не сказано, что изменилось |
| `Исправить баг` | какой — не понять без diff |
| `Изменения в parser.py и utils.py` | файлы видны и так; суть не названа |
| `Исправления по замечаниям ревью` | процесс, а не суть; замечаний через год не найти |
| `Добавить экспорт в Excel, поправить README и обновить зависимости` | три изменения — три коммита |

Хорошо:

```
Не терять последнюю строку CSV без перевода строки в конце

Разбор читал файл построчно и отбрасывал хвост после последнего \n,
поэтому выгрузки из бухгалтерии теряли итоговую строку. Теперь хвост
разбирается как обычная строка. Тест — файл без \n в конце.
```

```
Вынести проверку прав доступа в модуль access

Поведение не меняется. Следующим коммитом проверка понадобится в API
отчётов; копия в двух обработчиках со временем разошлась бы.
```

Многострочное сообщение: `git commit -m "<первая строка>" -m "<абзац>"` — каждый `-m` становится
абзацем; или `git commit -F <файл>`, файл — во временной папке вне рабочего дерева.

## Чего не класть (R-002, R-003)

Списки шаблонов проверяет код. Суждение нужно для того, что в них не попадает:

| Что | Как быть |
|---|---|
| Чужие правки в рабочем дереве, файлы неизвестного происхождения | Не добавлять; спросить человека |
| Следы работы: временные скрипты, заметки, вывод команд, `*.orig`, `*.rej`, патчи, снимки экрана | Удалить или держать во временной папке вне проекта |
| Отладка: печать, `breakpoint()`, закомментированный код, проверка, отключённая «на время» | Убрать до коммита |
| То, что пересобирается: отчёты покрытия, кэши, виртуальные окружения, собранные `.docx` и `.pdf` | Не в git; шаблон — в `.gitignore`, если это порождает проект у всех |
| Личные настройки редактора и инструментов, файлы агента | Скрыть через `.git/info/exclude`, не через `.gitignore`: тот виден всем и остаётся в истории |
| Секреты не по шаблону: токен в тесте, пароль в URL, ключ в примере конфига, настоящие персональные данные в фикстурах | Переменная окружения, заглушка, синтетические данные |
| Крупные двоичные файлы: данные, модели, архивы | Только по решению человека: git хранит их навсегда |
| Шум: файл изменён целиком ради трёх строк (концы строк, кодировка, BOM, автоформатер) | Вернуть исходный вид; нужное переформатирование — отдельным коммитом |

В коммит уже попало лишнее или секрет — `references/repair.md`.

## Перед коммитом

1. `git status --short` — про каждый файл знаешь, почему он изменился.
2. `git add <пути>` этого изменения. Внутри одного файла правки перемешаны — `references/repair.md`.
3. `git diff --staged` — прочитать целиком: нет отладки, секретов, шума, кусков другого изменения.
   `git diff --staged --check` — пробелы в концах строк и маркеры конфликтов.
4. Документация — по разделу выше: `git grep` по изменённым именам.
5. Тесты — на том, что войдёт в коммит. В рабочем дереве есть и другие правки — как проверить ровно
   индекс, `references/repair.md`.
6. Сообщение: что и зачем.
7. После — `git log -1 --stat`: в коммите ровно задуманное.
