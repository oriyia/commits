# Коммиты

Коммит читают потом и без контекста сессии: `git log` и `git blame` — когда и зачем изменилось
поведение, `git revert` — откат одного изменения, `git bisect` — где сломалось. Формальное
проверяют git-хуки проекта; здесь — то, что скриптом не проверить. Формат, принятый в проекте
(`CONTRIBUTING.md`), важнее примеров отсюда.

## Всегда

1. **Один коммит — одно логически завершённое изменение.** Набралось несколько — несколько
   коммитов, по одному на каждое.
2. **Коммить только то, что понимаешь.** Файл, про который не знаешь, откуда в нём правка, — не
   твой: возможно, человек работает рядом. Не добавлять, спросить.
3. **Индекс — по путям**: `git add <путь>…`. `git add -A`, `git add .`, `git commit -a` — только
   когда `git status` показал ровно это изменение и ничего больше.
4. **Хук отклонил коммит — коммита нет.** Исправить причину — код или сообщение — и снова
   `git add`, `git commit`. Не `--amend`: он перепишет предыдущий, уже хороший коммит. Не
   `--no-verify`: обход прячет ошибку, а не исправляет её.
5. **Проверку не ослаблять ради коммита**: не править список проверок проекта, настройки линтера
   и тестов, чтобы красное стало зелёным; чинить код (скилл `tests`). Не согласен с правилом —
   сказать человеку.
6. **Отправленное не переписывать.** `--amend`, `reset`, `rebase` — только для коммитов, которые
   никуда не ушли: ни на сервер, ни на носитель для переноса. Ошибку в отправленном исправляет
   новый коммит или `git revert`.
7. **Автор — человек, который отвечает за коммит**: `user.name`, `user.email`, `--author` не
   трогать.
8. **Когда коммитить — как договорено** в инструкциях проекта или в просьбе; не договорено —
   показать разбиение и сообщения и коммитить после согласия. Отправлять на сервер — только по
   просьбе и после долгих проверок проекта, если они есть.

## Одно ли это изменение

1. Сказать, что сделано, одной фразой без «а также» получается?
2. `git revert` этого коммита убирает ровно одну вещь и не ломает соседнее?
3. После коммита проект собирается, а тесты не падают?

«Нет» на первый или второй — коммитов должно быть больше. «Нет» на третий — коммит не закончен:
доделать или склеить с соседним. Код и тест на него — в одном коммите; переименование,
переформатирование, обновление зависимостей — отдельными. Остальные случаи —
`references/split.md`.

## Сообщение

Что изменилось и почему; как — видно из diff. Формальные правила задаёт проект и проверяет хук
commit-msg; своих нет — держись этих:

- в первой строке есть кириллица — сообщение по-русски;
- первая строка — не длиннее 72 символов;
- тело отделено от первой строки пустой строкой, иначе git склеит их в заголовок;
- тело — не больше 5 непустых строк;
- нет подписей инструментов: строк `Co-Authored-By:`, «Generated with …» и подобных.

**Первая строка** — суть изменения законченной фразой, глагол в неопределённой форме:
«Добавить…», «Исправить…», «Не терять…». Предмет — в словах поведения, а не в именах файлов; точки
в конце нет. Не укладывается в 72 символа — скорее всего, это два коммита.

**Тело** — почему: какая была проблема, почему решено так, что знать тому, кто будет обновлять или
откатывать. Не перечень сделанного и не отсылки к сессии («как просили», шаг плана, чат, память):
читатель — человек без контекста. Мелкому изменению хватает первой строки.

## Перед коммитом

1. `git status --short` — про каждый файл знаешь, почему он изменился.
2. `git add <пути>` этого изменения. Правки перемешаны внутри файла — `references/repair.md`.
3. `git diff --staged` — прочитать целиком: нет отладки, секретов, следов работы, шума, кусков
   другого изменения (`references/contents.md`). `git diff --staged --check` — пробелы в концах
   строк и маркеры конфликтов.
4. Изменённое имя — опцию, команду, поле конфига — найти `git grep -n "<имя>"` и поправить
   документацию в том же коммите.
5. Проверки проекта — те же, что запустит хук; красное чинить до коммита.
6. Сообщение — по разделу выше. После коммита — `git log -1 --stat`: в коммите ровно задуманное.

## По ситуации

| Ситуация | Файл |
|---|---|
| Несколько изменений сразу; неясно, как резать; коммиты слишком мелкие | `references/split.md` |
| Что не класть в коммит; какая документация входит в коммит | `references/contents.md` |
| Сомневаюсь в сообщении, нужны примеры; хук commit-msg отклонил сообщение | `references/message.md` |
| Правки перемешаны внутри файла; проверить ровно индекс; поправить, разрезать или склеить неотправленные коммиты; в коммит попал секрет | `references/repair.md` |
