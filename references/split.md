Когда читать: в рабочем дереве несколько изменений или неясно, одно ли это изменение; как резать рефакторинг, переименование, зависимости, документы; коммиты получаются слишком мелкими.

# Как резать

| Ситуация | Как резать |
|---|---|
| Рефакторинг готовит новое поведение | Два коммита: сначала рефакторинг (в теле — «поведение не меняется»), потом поведение |
| Переименование или перенос файла | Отдельный коммит без правок содержимого: иначе git может не узнать файл, и `git log --follow` оборвётся |
| Переформатирование, автоформатер, концы строк | Отдельный коммит, и в нём больше ничего |
| Исправление ошибки | Вместе с тестом, который её ловит |
| Новое поведение | Вместе с тестами на него: порознь история хранит либо красный тест, либо непроверенный код |
| Новая зависимость для новой функции | Вместе с кодом, который её использует; манифест и lock-файл — в одном коммите |
| Обновление версий зависимостей | Отдельный коммит |
| Команды проверок проекта | Отдельный коммит; в теле — почему выбран этот инструмент или изменена команда |
| Документы ожидаемого поведения, которые утверждает человек | Отдельный коммит, раньше тестов по ним |
| Сгенерированный файл, который проект хранит в git | Вместе с исходником, из которого он получен |
| Попутно замеченная ошибка или опечатка в другом месте | Отдельный коммит или пометка человеку, но не внутри текущего |

Слишком мелко — тоже плохо: «поправить опечатку в прошлом коммите», «шаг 2 из 5», «вернуть случайно
удалённое». До отправки такие коммиты склеиваются с тем, к которому относятся.

Резать по ходу дешевле, чем потом: делай изменения по одному и доводи каждое до коммита, прежде чем
браться за следующее. Перед рискованной правкой готовое — в коммит: это точка возврата.
