Когда читать: правки перемешаны внутри файла и их надо разнести по коммитам; надо проверить ровно то, что в индексе; поправить, разрезать или склеить коммиты, которые ещё никуда не ушли; в коммит попало лишнее или секрет.

# Разнести правки и поправить неотправленное

Проверь, что записанные здесь операции затронут только неотправленные коммиты. `git log @{u}..`
сравнивает текущую ветку с одной отслеживаемой веткой и само по себе не подтверждает, что коммит
никуда не ушёл. Если публикацию нельзя исключить, спроси человека.

Перед правкой истории:

- Проверь индекс и рабочее дерево через `git status --short`. Если все текущие правки твои и их
  нужно отложить, используй `git stash push --include-untracked` и запиши, какая запись создана.
  При чужих правках в дереве согласуй подготовку к переписыванию истории.
- Запиши текущий коммит через `git rev-parse HEAD`.

Если нужно отменить незавершённый `rebase`, используй `git rebase --abort`. Чтобы вернуться к
записанному коммиту после завершения операции, сначала сохрани нужные незакоммиченные правки.
Восстанови отложенные правки через `git stash apply --index <запись>`. Удали запись stash после
проверки индекса и рабочего дерева. При конфликте оставь запись для восстановления.

`<tmp>` ниже — временная папка вне рабочего дерева.

## Разнести правки внутри одного файла

`git add -p` спрашивает в терминале. Без терминала — два способа; после любого проверить:
`git diff --staged -- <файл>` — в индексе задуманное, `git diff -- <файл>` — в рабочем дереве остальное.
Ошибся — `git restore --staged <файл>` и заново: рабочее дерево оба способа сохраняют.

Правки разных изменений — в разных ханках (местах файла): через патч, лишние ханки удалить целиком.

```
git diff -- <файл> > <tmp>/part.patch
# в part.patch удалить лишние ханки: каждый — от строки @@ до следующей @@
git apply --cached --recount <tmp>/part.patch
```

Правки в соседних строках, в одном ханке: через копию файла. Строки в ханке не правь — легко
получить в индексе строки не в том порядке.

```
cp <файл> <tmp>/full
# в <файл> вернуть прежний вид всему, что относится к другому изменению
git add <файл>
cp <tmp>/full <файл>            # рабочее дерево — снова со всеми правками
```

## Проверить ровно то, что в индексе

Тесты в рабочем дереве видят и правки, которые в коммит не войдут, и неотслеживаемые файлы. Проще
всего не доводить до этого: держать в рабочем дереве одно изменение. Если не вышло — проверить индекс
в отдельной копии, не трогая рабочее дерево:

```
git worktree add --detach <tmp>/staged HEAD
git diff --staged --binary | git -C <tmp>/staged apply
# в <tmp>/staged — проверки проекта перед коммитом: линтер, форматер, модульные тесты
git worktree remove --force <tmp>/staged
```

Неотслеживаемого в новой копии нет: окружение (`.venv`, `node_modules`) и сборку подготовь в ней так
же, как в основной. На окружение основной копии не полагайся — оно может подхватить код из неё.

## Поправить последний коммит

```
git add <путь>; git commit --amend --no-edit              # забыт файл или правка
git commit --amend -m "<первая строка>" -m "<тело>"     # неудачное сообщение
git rm --cached <путь>; git commit --amend --no-edit      # лишний файл, который коммит добавил
git restore --staged --source=HEAD~1 <путь>
git commit --amend --no-edit                              # лишняя правка в файле, который был и раньше
```

В двух последних случаях правка остаётся в рабочем дереве. См. «Чего не класть» в `contents.md`.

## Разрезать коммит

Последний коммит, у которого есть родитель:

```
git reset HEAD~1                    # коммит снят, правки — в рабочем дереве
git log -1 --format=%B ORIG_HEAD    # прежнее сообщение, если пригодится
```

Дальше — по частям, как обычно.

Для более раннего коммита с родителем выполни `git rebase -i <хеш>~1`. В открывшемся списке
поставь `edit` напротив выбранного коммита. При автоматизации через `GIT_SEQUENCE_EDITOR`
сопоставь полный хеш с префиксом из списка и проверь, что найдена ровно одна строка.
После остановки проверь `HEAD` и выполни:

```
git reset HEAD~1                    # rebase остановился на этом коммите — снять его
# закоммитить по частям
git rebase --continue
```

Для первого коммита начни с `git rebase -i --root` и отметь первый коммит как `edit`. У него
нет родителя. Когда rebase остановится на нём, из корня репозитория выполни
`git rm -r --cached -- .`. Файлы останутся в рабочем дереве. Добавь в индекс первую часть и
запиши её через `git commit --amend`. Остальные части добавь отдельными коммитами, затем
выполни `git rebase --continue`.

## Склеить

Поправка к коммиту в середине серии:

```
git add <путь>
git commit --fixup=<хеш>
GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <хеш>~1
```

Для поправки к первому коммиту используй `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash --root`.

Серия «шаг 1 … шаг 5» одного изменения — одним коммитом:

```
git reset --soft <коммит перед серией>    # все правки серии — в индексе
git commit -m "<первая строка>" -m "<тело>"
```

## Секрет попал в коммит

- Сказать человеку сразу, даже если коммит не отправлен: менять ли секрет, решает он.
- Не отправлен: убери секрет из затронутой истории и проверь содержимое снимков коммитов,
  достижимых из проверяемых ссылок. Для проверки всего локального репозитория учти ветки,
  теги, stash и reflog. Не выводи значение секрета. Укажи, какие ссылки и снимки проверены.
  `git log -S` ищет изменения числа вхождений и может пропустить коммит, где секрет остался.
- Отправлен: секрет считается раскрытым и меняется. Новый коммит, который удаляет файл, из истории
  секрет не убирает; переписать историю на сервере — решение человека вместе с владельцами сервера.
